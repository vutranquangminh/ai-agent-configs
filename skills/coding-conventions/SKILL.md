# Stack Conventions (fallback)

Only applies when the repo has no local conventions (`.opencode/skills/`, `.agents/skills/`, `AGENTS.md`, `CLAUDE.md`). Local rules always win. Detect the stack from files at the repo root before applying a section.

## Universal rules (all stacks)

1. Generated artifacts are never hand-edited: DB migrations/schema diffs, lockfiles, build output, generated clients.
2. Work inside the project's environment (venv / node version manager / toolchain lockfile); use the pinned interpreter/runtime.
3. Comments and identifiers in English.
4. Files stay under ~300 lines; split by domain/feature when they grow.
5. Tests first for non-trivial logic: red → implement → green.
6. Mock all external services in tests (payments, email, LLM/AI, device APIs). Never call real third-party APIs from tests.
7. Never commit secrets, DB dumps, or large binaries.
8. Match the repo's linter/formatter config; run it on every changed file before claiming done. Fix issues in code, never via per-file ignores.
9. Boy scout rule: clean up only what the current task touches; no repo-wide reformat or drive-by refactors.

## Backend detection & structure

### Python / Django / DRF
Detect: `manage.py`, `pyproject.toml`/`requirements*` with Django.
- App layout: `api/<domain>/` (views, serializers, urls), `models/` (one file per model), `services/` (business logic), `tasks.py` (thin background-task wrappers), `tests/` mirroring the same split.
- Views (`ModelViewSet` preferred): auth + permissions + serialize + call service + respond. No business logic in views or serializers.
- Separate Create / Update / Display serializers, picked per action.
- Migrations: edit models, run `makemigrations`; never hand-write migration files.
- Tests: `SimpleTestCase`/plain pytest when no DB needed; `TestCase`/`pytest.mark.django_db` for models; `APITestCase` for endpoints; factories over manual creates.

### Java / Spring Boot
Detect: `pom.xml`/`build.gradle` with spring-boot.
- Package by feature, not by layer: `feature/{api,service,repository,model}` over a flat controller/service/dao tree.
- Controllers thin; business logic in services; repositories for data access. DTOs separate from entities; map at the boundary.
- Flyway/Liquibase migrations generated and versioned, never edited after release.
- Tests: JUnit 5 + Mockito for units, `@SpringBootTest`/Testcontainers sparingly for integration.

### Node / TypeScript backend (NestJS/Express/Fastify)
Detect: `package.json` with nestjs/express/fastify + `tsconfig.json`.
- Module/feature folders: `feature/{dto,entities,controller,service,module}` for Nest; `routes/ services/ repositories/` for plain Express/Fastify.
- DTO validation at the boundary (class-validator/zod); services return domain errors, controllers translate to HTTP.
- DB schema via ORM migrations generated by the tool, not hand-written.
- Tests: unit with the framework runner (jest/vitest), supertest for endpoints, in-memory or container DB for integration.

## Frontend detection & structure

### Next.js / React
Detect: `next.config.*`, `app/` or `pages/`, react in deps.
- App router conventions: route segments in `app/`, colocated components, `components/ui` for shared primitives, `lib/` for utilities and API clients.
- Server components by default; client components only for interactivity. Data fetching in server components/route handlers, not effects.
- State: server state via cache/fetch layer; minimal client state. No global store unless it already exists.
- Styling via the repo's existing system (Tailwind/CSS modules); don't introduce a second one.
- Tests: component behavior tests (Testing Library) over implementation snapshots; e2e only for critical flows.

### Vue / Nuxt
Detect: `nuxt.config.*` or `vue` in deps with `vite.config.*`.
- `composables/` for shared logic, `components/` colocated or shared, `stores/` only if Pinia already present.
- Composition API + `<script setup>`; keep components small, extract composables when logic grows.

## Output when bootstrapping

If the repo has no conventions at all, generate a concise `AGENTS.md` (or repo skill) capturing only what was detected — commands, structure, test/lint — show it to the user, and do not silently commit it.
